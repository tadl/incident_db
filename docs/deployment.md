# Dokku deployment and migration

The Dockerfile builds the app with Ruby 3.4.13 and libvips for image thumbnails. Dokku runs Puma on port 5000 and runs `bin/rails db:migrate` in the release phase before routing traffic to the new web process. The web and Sidekiq containers share the same database and attachment volume.

## Prepare the destination

- Create the app and its own PostgreSQL and Redis services. Use a supported PostgreSQL version and test a logical restore on the same major version before cutover. The app has no Memcached requirement. Keep both datastores private.
- Select the Dockerfile builder and map HTTP to container port 5000. Keep staging ingress disabled and set `dokku network:set APP bind-all-interfaces false` so the container port remains internal. Reach staging from the Dokku host or over an SSH tunnel.
- Configure a unique `SECRET_KEY_BASE`, the canonical HTTPS hostname in `APP_HOST` without a scheme, and the authorized Google Workspace domain in `AUTH_DOMAIN`. Provide Google OAuth client credentials with the canonical `https://APP_HOST/auth/google_oauth2/callback` registered. Set the app's staff role lists and notification settings as appropriate. Use `MAIL_DELIVERY_ENABLED=false` for staging and leave the production mail credentials and recipient lists out of that environment.
- Mount a restricted host directory at `/app/storage` with numeric owner and group 10001 for the container. If retaining the original legacy import files, put them in a separate restricted mount at `/app/import:ro`. The archived reports are already in PostgreSQL. Preserve that mount as an archive.
- Rehearse with synthetic cases, patron photos, and a suspension letter. Confirm the running container uses the expected Ruby version and can reach its PostgreSQL and Redis services. Exercise login and logout, draft and publish, attachment upload and thumbnail generation, and attachment access after restarting the container. Confirm the site denies unauthenticated access to records and attachment URLs. Verify production OAuth separately if staging has no Google client or DNS entry.

## Move the database and attachments

1. Keep the target web app private and its worker stopped while preparing the migration. Check the source and target database names, storage locations, free space, and expected schema. Prepare a private scratch directory with mode 0700 and set `umask 077` before writing migration artifacts.
2. Schedule a write freeze. Stop the source web process so every ingress path stops accepting writes. Drain the old Sidekiq queues before stopping the worker. Check queue, retry, and scheduled counts and account for their remaining jobs. Retain the old Redis service for rollback and job review. Use fresh Redis on the new host once pending work is accounted for.
3. Export PostgreSQL using the source Dokku plugin's logical export or `pg_dump --format=custom --no-owner --no-acl`. Transfer the dump over SSH into the restricted destination directory. Verify the export and transfer both succeeded and that `pg_restore --list` can read the archive. Restore into the new, empty PostgreSQL database using the target version's `pg_restore --single-transaction --exit-on-error --no-owner --no-acl -d DATABASE`. A restore failure blocks cutover. Keep dumps off development machines and out of logs and source control.
4. Copy the complete attachment directory while writes are frozen. Preserve the relative paths and file bytes. Set ownership to 10001:10001 and restrict directory and file modes on the destination. Transfer any archived import files separately. Compare file counts and checksums over the transferred bytes and check the destination for a readable object for each Active Storage blob key. Report aggregate results only.
5. Apply the Rails migrations to the restored database via the release phase. Compare source and restored table counts for existing records and verify the new incident-to-patron links on the destination. Smoke-test a historical incident, an attached image and letter, active suspensions, and logged-in staff permissions through the new proxy before opening the service. Keep mail delivery and the worker off until the target is ready to take writes.

## TLS, DNS, and rollback

Keep the current application hostname so existing OAuth redirect URLs and deep links still point to the correct service. As a bridge before DNS changes, transfer only the current full certificate chain and its private key directly between trusted proxy hosts. Restrict the key to root, reference the temporary files in the new virtual host, and confirm the certificate and key match. Back up any existing target virtual host configuration before editing it.

During cutover, `APP_ALIAS_HOST` can allow a second exact hostname while `APP_HOST` remains the hostname in email links. Register the OAuth callback for each hostname used to sign in. Once traffic moves, set `APP_HOST` to the live hostname and keep the preview hostname as the alias only for as long as it is needed.

The public proxy terminates HTTPS. Overwrite `Host` and `X-Forwarded-Host` with the canonical app hostname, `X-Forwarded-Proto` with `https`, and `X-Forwarded-Port` with `443`. Verify the Dokku proxy preserves these values on the second hop. Restrict access to the Dokku HTTP backend to the edge proxy. On both proxies, set the upload limit for intended attachment sizes and use an access log format that records `$uri` without `$request`, `$request_uri`, query parameters, or request bodies. Keep OAuth authorization codes and incident search terms out of proxy logs.

Validate the Nginx configuration before reload. Check TLS, redirects, staff login, and CSRF-protected actions against the new proxy using an explicit hostname override while public DNS still points to the source. Switch DNS in the approved window once verification passes. Keep the source frozen during TTL expiry so cached DNS cannot cause split writes. After DNS settles, issue a renewable certificate on the new proxy, switch to the Certbot-managed paths, and run a renewal dry run for this lineage.

Before the target accepts writes, rollback can restore the old DNS and resume the old services. Once the target accepts writes, freeze it and reconcile the new database and file changes before moving any traffic back. Keep the old services and migration artifacts restricted for the agreed rollback window. Remove temporary certificate copies and migration artifacts when that window closes.
